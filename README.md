# Gnoke Engine — Developer Guide

> One file to edit on the server. One file to edit on the client. Everything else is frozen.

---

## What is this?

Gnoke is a lightweight sync engine — think Firebase, but it's PHP + SQLite files you own and deploy yourself. Each deployment is for **one company**. Staff devices write data locally first, then sync to the cloud in the background.

---

## Deploy in 3 steps

**Use the configurator** — open `g-configurator.html` in your browser, fill in your values, and download the two generated config files. Drop them into place and upload.

```
g-configurator.html   →   generates gnoke-config.js   →  htdocs/
                      →   generates gnoke-config.php  →  htdocs/api/
```

That's it. Everything else is frozen — don't edit it.

## Collections

A collection is like a database table. You define it once in `gnoke-config.js` (via the configurator):

| Scope | Who sees the data |
|---|---|
| `'user'` | Only the logged-in user on this device |
| `'workspace'` | Everyone in the same branch / group |
| `'company'` | Everyone in the whole deployment |

## Reading and writing data

```js
// Write
const id = GnokeStore.save('invoices', { amount: 5000, status: 'pending' });

// Read
const all    = GnokeStore.query('invoices');
const open   = GnokeStore.query('invoices', r => r.status === 'pending');
const single = GnokeStore.getOne('invoices', id);

// Update
GnokeStore.update('invoices', id, { status: 'paid' });

// Delete (soft — syncs deletion to server)
GnokeStore.remove('invoices', id);

// React to changes (fires on every local write + server pull)
GnokeStore.onChange('invoices', records => renderTable(records));
```

## How login works

1. Staff enter phone/email + PIN.
2. Browser hashes `identifier + PIN` into a `device_id` (SHA-256 — PIN never sent to server).
3. Server looks up the profile, returns a **token**.
4. Token saved to `localStorage`. Every future sync request carries it.
5. On next page load, token is found and login is skipped automatically.

To log out: call `GNOKE_SECURE.signOut()` — clears token, returns to `index.html`.

**Inactivity logout is the app's responsibility.** Gnoke validates the session on every page load but does not run an inactivity timer. If you need it:

```js
// Sign out after 30 minutes idle
let idleTimer;
const IDLE_MS = 30 * 60 * 1000;
function resetIdle() { clearTimeout(idleTimer); idleTimer = setTimeout(() => GNOKE_SECURE.signOut(), IDLE_MS); }
['click','keydown','touchstart','scroll'].forEach(e => document.addEventListener(e, resetIdle));
resetIdle();
```

## How sync works

```
Staff device                    Server (api/index.php)
──────────────────              ──────────────────────
Write locally (instant)
       │
  every 30s ──── push ────────► saves to cloud DB
       │
  every 5min ◄─── pull ─────── returns updates
       │
GnokeStore.merge()
(UI re-renders via onChange)
```

- **Push** (`dispatch`): queued events sent in batches. Works offline — retries until connected.
- **Pull** (`get`): fetches records changed since last sync using a timestamp cursor.
- **Master pull** (`updates`): hard-overwrites local copy for read-only server lists (e.g. product catalogue).

## Account restore (lost device / forgotten PIN)

1. Admin calls `?action=generate-otp` with `admin_secret` + `user_id` → gets an 8-character OTP.
2. Admin sends OTP to the staff member (WhatsApp, SMS, etc.).
3. Staff enters phone/email + OTP + new PIN on the Restore screen.
4. Server issues a new token. Old tokens still work until explicitly revoked.

## Roles (optional)

Set in the configurator (or directly in `gnoke-config.php`):

```php
define('ROLES', [
    'operator' => ['save', 'get', 'dispatch', 'updates'],
    'admin'    => ['*'],
]);
```

Role is assigned when a user registers. `'*'` means full access. Leave `ROLES` as `[]` to skip role checks entirely.

## Common errors

| Error | Cause | Fix |
|---|---|---|
| `GnokeStore not loaded` | Script order wrong | Load `gnoke-store.js` before `gnoke-config.js` |
| `collection not defined` | Forgot to define in configurator | Add it to `gnoke-config.js` via configurator |
| `workspace_id is not set` | Login didn't complete before a write | Write only after login resolves |
| `Invalid or revoked token` | Token expired or wiped | User needs to sign in again |
| `Bad admin secret` | Wrong `ADMIN_SECRET` | Regenerate via configurator |
| `Cannot create database directory` | Server folder permissions | `chmod 750` the `gnoke-data/` folder |

## New client deployment

Run the configurator again. New endpoint, new `ADMIN_SECRET`, new `DB_PATH` (different filename). Each client is a completely separate SQLite file — they share no data.
